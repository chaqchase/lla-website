lla's source is at [github.com/chaqchase/lla](https://github.com/chaqchase/lla). This page has the commands you need to build it, test it and send a change. Contributions are licensed under MIT, the same as the project.

## Build from source

```bash
git clone https://github.com/chaqchase/lla.git
cd lla
cargo build -p lla
cargo run -- -l
```

`rust-toolchain.toml` pins the `stable` channel with `rustfmt`, `clippy` and the release targets, including `wasm32-wasip2`, so `rustup` installs what you need on first use. If you use Nix, `flake.nix` provides a dev shell and `.envrc` loads it through direnv.

The repository has no Makefile or justfile. Commands are `cargo`, plus the scripts in `scripts/` and `.github/scripts/`.

Three builds matter, because they compile different plugin code:

| Command | Plugin support |
| --- | --- |
| `cargo build -p lla` | Native plugins. The default `dynamic-plugins` feature. |
| `cargo build -p lla --features wasm-plugins` | Native plugins and WebAssembly components. |
| `cargo build -p lla --no-default-features` | None. A static stub replaces the plugin manager. |

## Find your way around

| Directory | What it holds |
| --- | --- |
| `lla/` | The CLI: argument parsing, listing, filters, formatters, the installer and the plugin host in `lla/src/plugin/`. |
| `interface/` | `lla_plugin_interface`: protobuf messages, manifest types and the native ABI. |
| `macros/` | `lla_plugin_sdk_macros`: the export macros. |
| `sdk/` | `lla_plugin_sdk`: the authoring API, the WIT world and test fixtures. |
| `utils/` | `lla_plugin_utils`: shared plugin helpers. |
| `plugins/` | The 37 bundled plugins, one crate each. |
| `themes/` | Theme files packaged as `themes.zip`. |
| `completions/` | Generated shell completions. |
| `docs/` | Documentation in the repository. |
| `scripts/` | Plugin bundle, catalog, protobuf and install-script tooling. |

The [architecture handbook](/docs/about/architecture#workspace-map) explains how these fit together.

## Run the checks

CI runs these commands on Linux, macOS, Windows AMD64 and Windows ARM64. Run them before you push.

```bash
cargo fmt --all -- --check
cargo clippy -p lla --all-targets -- -D warnings
cargo clippy -p lla --no-default-features --all-targets -- -D warnings
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
cargo test -p lla --features wasm-plugins
```

Then check the SDK fixtures:

```bash
cargo check --manifest-path sdk/tests/fixtures/minimal_native/Cargo.toml
cargo check --manifest-path sdk/tests/fixtures/custom_batch/Cargo.toml
cargo check --manifest-path sdk/tests/fixtures/wasm_component/Cargo.toml
cargo build --manifest-path sdk/tests/fixtures/wasm_component/Cargo.toml --target wasm32-wasip2
```

Some changes need more:

| You changed | Run |
| --- | --- |
| `install.sh` | `./scripts/test_install_sh.sh` |
| `install.ps1` | `./scripts/test_install_ps1.ps1` |
| `interface/src/plugin.proto` | `./scripts/generate_proto.sh` |
| A plugin's manifest | `./scripts/generate_plugins.sh`, which regenerates `docs/plugins/catalog.md` |
| The SDK, the host or any bundled plugin | The bundle check below |

```bash
./scripts/build_plugins.sh --target "$(rustc -vV | sed -n 's/^host: //p')"
./scripts/verify_plugins_v3.sh dist/plugins-<os>-<arch>
```

The bundle check needs `rustup` and Python 3 with `tomllib`.

CI also runs jobs that are awkward to repeat locally:

| Job | What it checks |
| --- | --- |
| NetBSD | `cargo build --release -p lla` natively, and `cargo tree -p lla -i wasmtime` must fail. |
| Build | Every release target, including the plugin archives. |
| Linux baseline | `.github/scripts/check_glibc_baseline.sh` rejects symbols newer than glibc 2.28. |
| musl | `.github/scripts/smoke_test_musl.sh` runs the static binary in Alpine. |
| Windows | PE import checks, the PowerShell installer test, and plugin archive verification. |

Two workflows open their own pull requests after you push. `generate-completions.yml` runs when `lla/src/commands/args.rs` changes on `main`, and `update-proto.yml` runs when `interface/src/plugin.proto` changes.

## Submit a change

```bash
git checkout -b fix/short-description
```

Add a note for user-visible changes under `## [Unreleased]` in `CHANGELOG.md`, which follows Keep a Changelog.

Commit messages follow Conventional Commits, as in the existing history:

```text
fix: print shell completions to stdout by default
feat(plugins): introduce Plugin Platform v3
chore: update shell completions
```

Add tests alongside new behavior. When you change flags or output, update `docs/` and the docs site in the same round of work.

Open the pull request against `main`. The CI path filters skip runs for pure documentation changes.

## Add a bundled plugin

A bundled plugin lives in `plugins/<name>/`. The workspace includes `plugins/*`, so no root change is needed.

```text
plugins/<name>/
├── Cargo.toml
├── plugin.toml
├── README.md
└── src/lib.rs
```

Follow the pattern of an existing plugin such as `plugins/file_hash`:

| File | Setting |
| --- | --- |
| `Cargo.toml` | `version` set to the product version, `crate-type = ["cdylib"]`, `lla_plugin_sdk = { path = "../../sdk" }`. |
| `plugin.toml` | `id = "dev.lla.<name>"`, `name` equal to the directory name, `version` set to the product version, `entrypoint` equal to the library name. |
| `README.md` | Actions, examples, dependencies and platform limits. |

`cargo test -p lla_plugin_interface` runs `every_workspace_plugin_has_a_valid_v3_manifest`, which reads each plugin's manifest and source and enforces these rules:

| Rule | Detail |
| --- | --- |
| Name | The manifest `name` matches the directory. |
| Export | The source uses the export macro for its `runtime`. |
| Old API | The source doesn't mention `handle_raw_request`, `PluginRequest`, `PluginResponse` or `ProtobufHandler`. |
| Decorators | A plugin with `decorates_entries` has `fn decorate_entry` and `fn decorate_batch`, and sets typed values through `insert_field(`, `promote_` or `typed_fields`. |
| Actions | A plugin with actions has `fn run_action` and `fn registered_actions`. |
| Descriptions | An action description doesn't start with `Run the `. |
| Examples | Every example starts with `lla plugin run <name> <id>`. |
| Arguments | No argument is named `args`. |
| Clipboard | Source using `arboard::Clipboard` declares `clipboard = true`. |
| URLs | Source running `xdg-open` or `Command::new("open")` declares `open_url = true`. |
| Processes | Source using `Command::new` declares `process = true`. |

The test reads source text and doesn't execute anything, so `lla plugin doctor` still has to pass. Run the full check:

```bash
cargo test -p lla_plugin_interface
cargo clippy -p my_plugin --all-targets -- -D warnings
./scripts/generate_plugins.sh
./scripts/build_plugins.sh --target "$(rustc -vV | sed -n 's/^host: //p')"
./scripts/verify_plugins_v3.sh dist/plugins-<os>-<arch>
```

Don't edit `docs/plugins/catalog.md` by hand. A new plugin also needs a page in the docs site under `content/docs/first-party-plugins/`.

To write the plugin itself, use the [tutorial](/docs/guides/plugin-development-tutorial) and [Developing plugins](/docs/plugins/developing). A plugin doesn't have to be bundled to be useful: anyone can install yours with `lla install --git`.

## Change the docs

Documentation lives in two repositories:

| Location | Contents |
| --- | --- |
| `docs/` in `chaqchase/lla` | Markdown guides and the handbook, kept with the code. |
| `content/docs/` in [`chaqchase/lla-website`](https://github.com/chaqchase/lla-website) | This site, as MDX. |

The site's sections map to directories:

```text
content/docs/
├── about/                 Introduction, installation, architecture handbook
├── usage/                 Views, filtering, navigation, configuration, machine output
├── plugins/               Plugin platform: overview, developing, manifest
├── first-party-plugins/   One page per bundled plugin
├── guides/                Tutorials
├── reference/             CLI reference
└── support/               FAQ, troubleshooting, contributing, releasing
```

Run every command you document against a real binary and paste its real output. When the docs and the program disagree, fix the docs or file a bug.

## Report a bug

Open an issue at [github.com/chaqchase/lla/issues](https://github.com/chaqchase/lla/issues) with what a maintainer needs to reproduce it:

```bash
lla --version
lla config show-effective
lla plugin doctor
```

Include your OS and terminal, the exact command, what you expected, and what you got. Check the [troubleshooting page](/docs/support/troubleshooting) first.

For a feature request, describe the problem and show the command you wish you could run.
